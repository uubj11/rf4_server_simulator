# 网关停止按序收尾：承接状态必须在数据库关闭前落库

## Problem Statement

玩家在钓鱼途中客户端弹出「未连接到游戏服务器」，重连回来后渔具状态、溜鱼进度
和刚入护的鱼都没了；运维侧同一时间段看到两处异常对不上：

- `logs/gateway.log` 里两次 `handoff 保存失败 err="sql: database is closed"`，
  且 `"gateway 已退出"` 打印在会话收尾之前 —— 网关明明是想保存承接状态的，
  但数据库已经被关掉，状态直接丢失；
- `logs/gameserver.log` 里 207 条「信封解析失败」，长度从 65 字节涨到 129 字节，
  每分钟二十多条持续重试，首字节每次都不同（`0x3C`/`0xEB`/`0xF3`…），
  而正常信封首字节恒为 `0x01` —— 说明密文被当成明文在读，密码流已经失步。

也就是说这不是一个点上的 bug，而是「网关收尾 → 状态承接 → 密码流续接」这条链上
三处独立缺陷叠在一起，全部来自首个发布提交，与本次改动之前的本地分支无关：

1. **收尾顺序**：`RealtimeServer.Close` 只关监听、不等会话收尾；`cmd/gateway` 的
   关闭序紧跟其后就关数据库。承接状态因此没机会落库。
2. **快照自相矛盾**：导出 RC4 状态（拷 256 字节 S-box，慢）与加解密（改 i/j，快）
   没有共用同一把锁，快照可能拿到「旧 S-box + 新 i/j」。承接方据此续流，
   此后每一帧都错位，且**无法自愈** —— 这正是 207 条解析失败持续到会话被关闭的原因。
3. **握手吞帧**：hermes 握手阶段一次性消费掉整段解析结果，而客户端经常在同一个
   TCP 段里紧跟握手发出第一个业务帧，该帧被吞：客户端已推进密码流、服务端没有，
   从第一条业务帧起就错位。

## Solution

网关停止变成有明确顺序、有明确时间上界的过程：先停止接受新连接，再让每个在线会话
把承接状态落库，最后才关数据库和隧道；即使隧道此时正在重连退避，也不会把收尾拖到
被系统强杀。承接状态本身不会自相矛盾，重连的客户端以同一段连续密码流恢复；握手
阶段也不会再吞掉紧跟其后的业务帧。玩家看到的效果是：短暂网络中断后会话原地恢复，
钓鱼进度不丢。

## User Stories

1. 作为玩家，钓鱼途中网络抖一下重连回来，渔具、溜鱼进度和已入护的鱼都还在。
2. 作为运维，`systemctl restart` 网关时进程在自己退出，而不是等 90 秒被 SIGKILL。
3. 边界：隧道断开且多个会话同时收尾时，关闭耗时与会话数无关，不随会话数线性变长。
4. 边界：重连确实没有可用承接状态时（例如玩家跨版本、状态已过期），服务端明确告警
   并新建密码流，而不是静默地发一段客户端解不开的数据。
5. 边界：承接状态读取出错（数据库真错误）时不能再被当成「无状态」，否则同样的
   失步会以第二种路径重现。
6. 边界：重连时隧道仍不可用（OPEN 失败）不能让承接状态被提前删除 —— 玩家这次重连
   失败了，下次重连还得能接上。
7. 边界：隧道已经换了新连接时，旧连接的读循环不得再把新连接标成断线，否则刚恢复的
   会话会被自己人踢掉。

## Implementation Decisions

- `internal/proto`：给 RC4 流加互斥，`Crypt` 与 `Export` 共用同一把锁，快照与推进
  不再可能撕裂。不改 `Restore`，不改任何报文字段。
- `internal/gateway`（`realtime.go`）：`Close` 改为「关监听 → 丢弃在线会话 →
  等写者收尾」；新增关闭中标志与写者登记，保证等待期间不会再有新的写者加入。
  只等写者、不等整个会话：会话收尾随后还要走隧道 `sendClose`，而隧道管理器在断线
  退避期间无法立即返回，全等会把关闭拖到分钟级（见 Further Notes）。
- `internal/gateway`（`tunnelclient.go`）：`getConn` 的重连退避与拨号移出保护字段的
  互斥（另用独立锁串行化拨号），`Close` 只置关闭标志并在锁外关连接。这样关闭链
  不必等任何一次退避或拨号结束。
- `internal/gateway`（`realtime.go`）：握手只消费到握手帧为止，其后同段到达的业务帧
  交回正常读循环。
- `internal/gateway`（`sqlitestore.go`）：承接状态读取只在「无此行」时返回空，
  其他错误如实上抛，并在重连未取到状态时打 WARN + 计数。
- `internal/gateway`（`realtime.go`）：承接状态的读取结果分三支处理 —— 取到状态则
  承接；读取出错则**中止本次重连并保留状态**（不再新建密码流）；确实没有状态才按
  「无状态」策略新建并告警。承接状态的删除移到「隧道 OPEN 成功 + 写者已登记」之后、
  写者启动之前：早于此会因 OPEN 失败留下孤儿，晚于此则有写者先存、随后被删的竞态。
- `internal/gateway`（`tunnelclient.go`）：隧道连接带**代际号**，每成功拨号一次加一，
  读循环带着自己的代际跑；退出时只在「自己的代际仍是当前代际」时才清连接、报离线并
  清理会话。只看 `m.conn` 指针不够：发送失败会先把 `m.conn` 清成 nil，而 nil 同时
  意味着「还没建新连接」（必须报离线并踢会话）和「已被更新代际顶替」（必须保持沉默），
  两种含义处理相反。旧连接只关闭自己，不碰在线指标、离线回调与会话清理，避免把已换好
  的新连接误标为断线并踢掉其上的健康会话。
- `internal/gateway`（`realtime.go`）：承接状态按 token 记录**当前接管者**（token →
  会话 id），新会话在启动写者之前夺取所有权，旧会话的周期性快照因此一律作废。
  所有权校验与「导出快照 + 落库」必须在同一个 per-token 临界区里完成：只做一次
  布尔检查会留下 TOCTOU 窗口——旧写者通过校验后被调度走，新会话趁机接管并写入
  更新的 `next_wire_id`，随后旧写者把自己那份更旧的快照写回去，数据库回退到更旧
  的进度。临界区用固定条纹（64 条）而非按 token 建锁：token 会不断新增，按需建锁
  会让这张表无界增长；同一条纹上的不同 token 偶尔串行，代价可忽略。
  只按会话 id 判断是不够的 —— 主服接管的是它自己那边的会话，网关侧旧 `clientSession`
  仍在跑，它不知道已被顶替；而 `SaveHandoff` 是无条件 upsert，谁最后写谁生效。
  旧会话收尾时只在「自己仍是当前所有者」时释放，不得抹掉新会话的所有权。
- `internal/testutil`：测试桩暴露隧道管理器与「模拟主服侧隧道中断」的能力，供关闭链
  延迟回归使用；网关装配增加「注入自定义存储」的入口，供「读库出错」一类分支测试
  包一层故障存储，生产代码不加测试钩子。
- 数据与迁移：**不改表结构、不加迁移**。承接状态表在此之前已存在，本次只修读写时机
  与错误处理，旧库直接可用。
- 兼容：客户端基线 `4.0.25034`，无协议字段/`args code` 变更，客户端无需改动。
  回滚方式：按文件回退上述四处实现改动（对应三个 commit），测试文件可保留。

## Testing Decisions

- 测哪一层：**行为层**，用现有 `internal/testutil` 的假客户端 + 桩主服起真实网关与
  真实 SQLite，不新增模拟层。协议层不动，因此不需要编解码回环用例。
- 期望值来自哪：关闭耗时上界取 systemd 默认停止超时（`TimeoutStopUSec=1m30s`）的
  安全余量，钉 10s；承接状态的存在性与 `next_wire_id` 单调性来自「已发出的帧数」这一
  独立可数量，不用被测代码回算。
- 回滚后变红（已实测）：
  - 回退 `tunnelclient.go` 的退避移出锁 → `TestShutdownNotBlockedByTunnelBackoff`
    **150 秒超时失败**，栈停在 `internal/gateway/tunnelclient.go` 的 `time.Sleep`；
  - 回退 `realtime.go` 的关闭等待 → `TestHandoffPersistedOnClose` 变红
    （「关闭后没有 handoff」）；
  - 回退握手只消费到握手帧 → `TestHandoffResumeKeepsKeystream` 连续 3/3 变红
    （「等待响应超时」），恢复后 5/5 绿。
  - 回退承接状态的删除时机（移回「读到就删」）→ `TestReconnectOpenFailureKeepsHandoff`
    变红（「重连 OPEN 失败后承接状态被删除了」）。
  - 回退读库错误的三分支（合回「出错即当无状态」）→ `TestLoadHandoffErrorAbortsReconnect`
    变红（桩主服收到的 OPEN 数从 1 涨到 2，说明仍在新建会话）。
  - 回退隧道读循环的「是否当前连接」判断 → `TestOldReadLoopDoesNotClobberNewConn`
    变红（「旧连接的读循环 dropAll 杀掉了新隧道上的健康会话」）。
    `TestCurrentReadLoopStillReportsOffline` 在该回退下仍为绿：它守的是正常路径不被
    收紧改坏，不是缺陷复现用例。
  - 回退「按 token 的接管所有权」（去掉 `saveHandoff` 里的 `ownsToken` 守卫）→
    `TestOldWriterDoesNotOverwriteNewHandoff` 变红：`next_wire_id` 从新会话存下的
    6 被旧写者覆盖回 3，客户端下次重连会从更早的位置续流。该用例的时序是确定的
    —— 先等新会话落库并退出，再留出整个旧写者周期（2s+），让「最后一次写入」只
    可能来自旧写者；否则两个写者每 2 秒各存一次，靠抢时序碰运气，去掉守卫也会
    通过，用例就没有判别力。
  - 回退「所有权校验与落库的原子性」（去掉 per-token 临界区、只留布尔检查）→
    `TestOwnershipCheckIsAtomicWithSave` 变红：接管在旧写者落库途中就完成了
    （0.004s 内失败，不是靠时序碰运气）。判别方式是让存储层在写库处阻塞，把
    「已通过校验、尚未落库」这个窗口钉死，再在窗口里发起接管——修复到位时接管
    必须等旧写者落库完成才可能拿到所有权。
    注意该用例**必须**是内部测试（`package gateway`）：行为层验证过两版都不成立。
    第一版看最终值，新旧会话每 2 秒各存一次，最终值由最后一次周期写入决定，
    去掉修复也照样 PASS；第二版看落库顺序，但完整网关上新会话的推进要等服务端
    接管完成，窗口里根本推不动，同样区分不出来。这两次失败已记进 Further Notes。
  - 回退隧道读循环的「连接代际」判断（改回只比 `m.conn` 指针）→
    `TestWriteFailureStillDropsSessions` 变红（「写失败清空连接后读循环跳过了
    dropAll」）。这里不能用 `m.conn == nil` 当判据：`send()` 写失败会先把它清成
    nil，而 nil 同时意味着「还没建新连接」（必须上报离线）和「已被更新代际顶替」
    （必须保持沉默），两种含义处理相反，只能靠代际号区分。
- 未覆盖：RC4 快照撕裂是并发窗口问题，当前**没有**能稳定复现的用例（多次运行也不一定
  命中），本次靠互斥本身保证，不声称有用例锁定；详见 Further Notes。

## Out of Scope

- `cmd/launcher` 在非 Windows 平台无法编译（引 `golang.org/x/sys/windows`）—— 既有问题，
  与本改动无关，CI 相应地不测该包。
- `-race` 下 `initRealtimeMetrics` / `initTunnelMetrics` 的全局指标重赋值竞争 ——
  既有问题，主分支基线同样复现，CI 不跑 `-race`。
- 真实客户端跨版本重连、长时间连续钓鱼的稳定性 —— 需要人工实机验收，本次未做
  （见 `docs/client-checklist.md` 的「重连与稳定性」四条）。
- 承接状态的过期/清理策略，以及隧道协议本身的健壮性。

## Further Notes

- `[事实]` 网关关闭序在 `cmd/gateway` 里是「登录服 → 实时服 → 隧道 → 可观测 → 数据库」，
  数据库最后关；但实时服此前不等待，所以顺序正确也无法保证承接状态先落库。
- `[事实]` 会话收尾里承接状态保存在等待写者时完成，早于隧道 `sendClose`；
  因此「只等写者」既满足数据正确性，也避免被隧道退避拖住。全等整个会话的第一版实现
  实测使关闭耗时随会话数线性增长（1 会话 0.5s / 5 会话 60.5s / 20 会话 >300s），
  被系统 90 秒停止超时 SIGKILL 后数据库反而先关，比不修更糟 —— 这也是本条约束的由来。
- `[推断]` 207 条解析失败里首字节的随机分布与 RC4 密文特征一致；据此判定是密文被当明文，
  而非帧格式错误。真实客户端未接入验证。
- `[假设]` 客户端在同一 TCP 段紧跟握手发首帧是常态而非特例；该假设来自抓包观察，
  未做多版本统计。
- 未验证：真实客户端断线重连、跨版本承接、长时间连续钓鱼，均未实机验收。
