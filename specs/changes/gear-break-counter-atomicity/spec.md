## Problem Statement

玩家的渔轮损坏后，统计页上的「断轮次数」会少记，而损坏本身已经发生，玩家重连、重进钓场都不会补回来：

1. **轮子坏了，计数却没涨。** 断轮时耐久先被写到 0（轮子立刻不可用、抛投被拦），计数却由另一条独立写入完成。这条写入一旦失败——进程在两次写入之间退出、库忙、磁盘写满——轮子已经损坏但计数永久丢失，玩家再也没法把这次记录补回来。
2. **磨损磨穿的轮子完全不计。** 轮内摩擦片被磨到寿命归零时，聚合后的轮体耐久同样是 0，轮子同样收不了线、同样要修理或换片，但这条路径从来没有增加过断轮计数。玩家的实际体感是「我磨坏了一个轮子」，统计页上却是 0。
3. **计数失败时玩家拿到一个自相矛盾的结果。** 耐久已归零、断件回执也已经发出，唯独计数没写成功。玩家侧看到轮子坏了，账本侧没有这次损坏的证据。

影响：所有会断轮、会磨穿摩擦片的玩家；统计页与图鉴类进度对不上账，且无法事后修复。

## Solution

把「轮体耐久从正数变成 0」当成唯一权威判据，并在同一次写入里完成计数：

1. 断轮（客户端上报 17/9 裁决为渔轮）时，计数与耐久、损伤日志在**同一个事务**里提交：计数写不进去就整笔回滚，轮子还是好的，玩家可以重试，绝不会出现「坏了但没记」。
2. 零件磨损把聚合轮体耐久磨到 0 时，也计入断轮次数——判据是本次写入前的耐久大于 0、写入后等于 0 这个状态转换，而不是某条路径有没有打上「已损坏」标记。同一件装备在一次损坏中只会被计一次。
3. 已经损坏的装备重复上报不再计数，也不会重复写损伤日志。

玩家侧可见变化：统计页的断轮次数等于「玩家实际弄坏过的渔轮个数」，磨穿摩擦片也算；断轮失败时玩家会收到失败回执并可重试，而不是拿到一个计数缺失的静默结果。

## User Stories

1. 作为玩家，我希望客户端上报 17/9 且裁决结果是渔轮时，断轮次数立刻加 1，以便统计页反映我的真实损耗。
2. 作为玩家，我希望把渔轮内部摩擦片磨到寿命归零、轮子彻底收不了线时，这次损坏同样被计入断轮次数，以便「磨坏」和「拉断」在账本上是同一件事。
3. 作为玩家，我希望同一个已损坏的渔轮被重复上报（重复帧、重试同一个请求、同一时刻并发多个请求）时，断轮次数只加 1，损伤历史也只有一条，以便不会因为网络重试而虚增记录。
4. 作为玩家，我希望断轮写入失败时我的轮子保持损坏前的耐久、并且我收到失败回执可以重试，以便不会出现「轮子坏了但没记账」这种既不能玩也补不回来的状态。
5. 边界：其他玩家的渔轮损坏不计入我的计数；我的计数也不会因为别人的上报而变化。

## Implementation Decisions

**计数入口统一到存储层。** 在 `internal/store` 的装备损伤仓库里新增一个「按执行器累加玩家计数器」的函数，签名接受 `SQLExecer`（`*sql.DB` 与 `*sql.Tx` 共同实现），SQL 为 `INSERT ... ON CONFLICT(uid,key) DO UPDATE SET value=value+1`。这样事务内外共用同一段 SQL，不再有第二份手写语句。

**断轮路径（客户端 17/9 裁决为渔轮）。** 在已存在的事务里，于耐久归零与损伤日志写入之后、提交之前累加 `reel_breaks`，失败即返回错误让事务回滚。该事务已有幂等守卫：耐久已经不大于 0 时直接返回「渔轮已损坏」哨兵错误，所以重复上报不会二次计数。

**零件磨损路径（摩擦片磨穿导致聚合耐久归零）。** 在泄力打滑写库路径与搏鱼磨损结算路径上，按「写入前耐久 > 0 且写入后耐久 == 0」判断并累加同一个计数器。两条路径都把轮体字段、性能参数、损伤日志（适用时）与计数器放进同一事务；计数写入失败时整笔回滚，耐久不会先归零。

**不改 `ReelBroken` 的语义。** 该标记只表示「客户端上报断件」，摩擦片磨穿仍然只标 `FrictionWorn`——摩擦片是消耗件，磨穿是泄力失效而不是结构断裂，客户端据此给出不同的提示。计数与这个标记解耦，改用耐久状态转换判定。

**协议与字段不变。** 不新增命令、不改任何响应字段与数组元素，客户端版本基线 `4.0.25034` 不受影响，旧档无需迁移。

**数据与迁移。** 复用既有的 `player_counters(uid, key, value)` 表，不新增表、不加列，无需迁移。

**兼容与回滚。** 回滚只需还原代码，计数器里已有的值属于正常累计，不回退也不影响读取；`player_counters` 缺行时读取侧本来就有 `COALESCE(...,0)` 兜底。

## Testing Decisions

**测试层级：存储层 + 行为层（真实 SQLite，走真实写库路径）。** 所有断言都落在真实数据库的最终状态上，不 mock 存储。

**测试一：磨穿摩擦片要计数。** 用带独立摩擦片子件的竿/轮夹具，把摩擦片预置到只剩约 1.5 步寿命，连续两次泄力打滑把它磨穿。断言：摩擦片标记为磨穿、`ReelBroken` 仍为假、轮体耐久为 0、`player_counters` 中 `reel_breaks` 为 1；再打一次滑，仍然是 1。

**测试二：计数失败要回滚耐久。** 分别覆盖 17/9 断轮、泄力打滑磨穿和搏鱼受力结算三条路径。先把 `player_counters` 表删掉制造真实写入失败，再执行对应路径。断言：调用返回错误或失败；轮体耐久、性能参数和损伤日志均保持原值。

**期望值来源。** 全部是字面量：`1`、`0`、以及损坏前读到的耐久值本身，不由被测代码再算一遍。

**回滚后哪些测试会变红。** 撤掉计数写入后，「磨穿摩擦片要计数」直接红（`reel_breaks` 为 0）；撤掉同事务改造后，「计数失败要回滚耐久」红（耐久被归零且损伤日志留下）。两者互为否定对照，已实测：撤掉生产改动两条都红，恢复后两条都绿。

## Out of Scope

- **不认领统计页 321 响应里 f11/f13/f22 等槽位的语义。** 本次只保证 `reel_breaks` 这个计数器本身在数据库里正确累加；哪些槽位展示它、展示成什么文案，属于统计页记录卡的分族工作（见 `specs/changes/stats-tackle-family-and-gear-breaks/spec.md`），不做猜测性占用。
- **不改 `ReelBroken` / `ReelDamaged` 的既有语义与客户端提示分派。**
- **不给其他耐久写入点补计数。** 前导钢线磨损、钓获时的组件磨损、换件/修理把耐久上调，这些都不是轮体归零，不计数。
- **不做历史数据回填。** 改造前已经丢失的断轮次数无法还原，不回填、不估算。

## Further Notes

- `[事实]` 断轮路径的耐久归零与损伤日志本来就在同一个事务里，计数原先在事务提交之后由独立语句写入且错误被丢弃——这是本次要修的账实不符根源。
- `[事实]` 摩擦片磨穿后聚合轮体耐久确实归零，既有测试 `TestReelSlipWearsFrictionWasherOut` 已断言这一点；但同一条测试也断言此时 `ReelBroken` 为假，所以计数不能挂在该标记上。
- `[事实]` 主库连接池固定为一条物理连接，因此持有事务期间禁止再调查库函数；计数必须真正走事务句柄，不能「在事务里另开一条连接写」。
- `[推断]` 并发重复上报只计一次，是因为事务内的耐久守卫在第二次进来时读到耐久已不大于 0 并直接返回哨兵错误；这一点由既有并发探针与本 PR 的重复上报断言共同覆盖，未在本次新增压测。
- `[假设]` 统计页确实把 `reel_breaks` 当作断轮次数展示；该假设不影响本 PR 的正确性，只影响玩家能否立刻在对的地方看到数字。
- 未实机验证：本次全部证据来自自动化测试与门禁命令输出，未在真实客户端上跑断轮/磨穿场景。
