# 工坊预览与支付确认分离

Status: done

## Problem Statement

玩家选择配件、确认银币支付后提示成功，磨损和界面余额却不更新；反复选择替代品还会在确认之前扣钱。

## Solution

选择时只预览修复后的装备，确认支付时才一次性扣费并保存所选部件；成功后刷新装备和余额。轻微磨损也能修复，未选部件保持不变。

## User Stories

1. 选择或取消替代品不扣费、不改变存档。
2. 确认后所选型号和耐久实际更新，余额同步更新。
3. 微小磨损按客户端最低修理报价 1 银币计费，已完好部件重复确认不扣费。

## Implementation Decisions

- `econ_market.go` 分开注册 21/3 预览与 21/4 确认，共用部件计算；仅确认进入经济事务，预览与确认均沿用通用请求回执。
- 保持物品响应类型及字段编码不变。客户端基线 4.0.25034。
- 同型号工单报价与逐件修理报价统一；有磨损时最低 100 分（1 银币），完好时 0。替代型号保留原定价。
- 更新被修理/替换子件版本，提交后推送 4/22 和 2/1；鱼竿重建保留子件版本。
- 不改数据库结构、静态库和既有存档。

## Testing Decisions

- 注册路由回归：两次预览返回所选型号但不写装备、余额或推送；确认只扣一次并推送装备与档案。
- 真实 SQLite：99.95% 完好部件修复至 100%，客户端提交 100 分报价，扣 1 银币，重放不再扣费。
- 报价、子件版本、未选部件、事务失败回滚及现有工坊测试。
- 全量 test、vet、build、doccheck；部署后实机复核直接修理及替代品。

## Out of Scope

不校准官服价格，不批量修改玩家历史余额或装备。

## Further Notes

- [事实] 本地客户端交互跟踪：选择型号时发送 21/3、f3=0；银币确认时发送 21/4、f2=0、f3=所选工单费用。重复预览会连续发送 21/3。故原有“21/4 是金币通道”注释错误。
- [事实] 修复前 21/3 写入换件流水；21/4 因型号已变成当前型号而走零费用返回。轻微磨损经四舍五入为零后也返回原对象。
- [事实] 成功路径缺少余额档案推送；新子件版本为零，同槽换件复用 GUID。
- [事实] 首次部署后，客户端对服务端报价 1 分的轻微磨损手柄提交 21/4、f3=100，触发 `client=100 server=1` 校验失败。最低修理价修正为 100 分，并以同一确认价格回归。
- 原始报文与玩家记录仅保存在本地忽略目录，不提交。
