# 自制拟饵选钩与固定槽位

Status: done

## Problem Statement

制作流程调用通用物品构造器，未选钩时也会填入定义中的出厂钩。只发送已安装钩的紧凑数组，又会使双槽拟饵在重开详情或重登后失去空槽入口。制作与手动装卸需要共享槽位身份，且不能改变鱼钩归属或重复退包。

## Solution

制作只安装请求中选中的真实背包鱼钩。已安装钩仍以紧凑数组保存在 FieldsJSON，额外在既有 KV 中保存固定槽位到鱼钩 GUID 的映射。发送物品树时按定义容量投影完整 args(60)，未占用的位置使用协议空值元素。该行为默认生效，无实验环境变量。

## User Stories

1. 未选钩制作后没有鱼钩，但仍能看到并使用全部配置槽位。
2. 只选第一槽或第二槽时，实际钩子保持在对应位置。
3. 装卸、重新打开页面、重登和服务端重启不丢失空槽。
4. 普通购买的拟饵保留出厂钩并正常显示在背包中。
5. 扣料、产出和钩归属更新一起提交，任一步失败均回滚。

## Implementation Decisions

- `craft_ops.go` / `craft_lure.go` 从材料槽中分离 `plug_hook`、`plug_hook_2`，以 GUID 校验归属、背包状态、数量、耐久和钩品类。第三字符串只用于型号一致性校验，不作为实例标识。选中的钩不能再作为普通材料消耗。
- `attachLureHookTx` 复用手动装钩的事务内归属转移与子树构造，制作方负责提交或回滚。购买仍使用通用构造器的出厂钩逻辑。
- `lure_hook_positions:<拟饵GUID>` 保存固定长度的 GUID 列表，内部空位为空字符串。FieldsJSON 只保存真实钩，不落库 null 元素或虚构物品；不改表结构、不批量迁移历史物品。
- 没有位置记录的购买/历史拟饵，按原装钩 GUID 恢复已知位置，其余钩按现有顺序放入空位。仅 `sql.ErrNoRows` 视为可选记录缺失，其他数据库错误仍返回。无法恢复早已丢失的非原装钩历史位置。
- `ItemToTree` 统一投影制作响应、库存详情和后续更新。拟饵仍为 type 141，f0 仍是 args(60)，已装钩仍为 type 131；数组本身始终非 null，无钩槽配置时为空 args(60)。不新增 wire 字段，不把 f1 解释成槽位索引。
- 手动装卸将稳定 UI 槽位映射到紧凑存储下标。越界槽位、重复卸空位和陈旧提交拒绝；已有 GUID 校验、原装钩退包一次及事务回滚语义保留。
- 固定槽位投影不改变存储中的活动钩选择与搏鱼 flags。上游 #452 已合并且包含在开发基线中；其挂载拟饵整树仍经 ItemToTree 构造，单钩物理查询按 GUID 跳过空位置。

## Protocol Evidence and Review

客户端基线为 4.0.25034。

- 制作对照请求确认：选择两钩时材料槽数量从 4 增至 6，新增 `plug_hook`、`plug_hook_2`，分别包含实例 GUID 和型号；槽名可区分只选第二槽的情况。
- 用户官服实测：支持两槽的手工拟饵，无论选零、一、两钩都保留两个可用槽位。该行为证据不等于已取得官服空槽响应编码。
- 当前客户端离线静态分析与模拟器实际响应解码支持：实例钩数组的空元素可以保留位置。模拟器输出 `[空, 空]`、`[钩, 空]`、`[空, 钩]`、`[钩, 钩]`，均经用户客户端回归。
- 本提案使用协议空值 `proto.Null()` 表示数组中的空位置；不使用 elem_null、虚假钩或占位对象，不关闭响应契约校验。无官方空槽响应抓包，不声称复原官方服务器的全部实现。
- **待维护者评审的文档差异**：`specs/capabilities/rig-assembly.md` 第 3 节和 `specs/changes/lure-hook-official-semantics/spec.md` 将短缩视为通用客户端要求，与本轮行为证据不一致。本 PR 提议区分紧凑持久化与固定位置 wire 数组；保留旧文档供评审，不将旧文档直接改写为既定结论。

## Testing Decisions

使用现有 SQLite、制作请求、装配与协议编解码测试辅助函数，不引入新测试框架。

- 四种制作选择：检查 803 两处物品树、槽位顺序、真实钩 GUID、归属、无额外钩物品，以及无钩存储的显式空 args(60)。
- 关闭并重开数据库、执行既有物品修复后，槽位仍保持；序列化不修改 FieldsJSON。
- 两槽分别拆装、先装第二槽、替换、退包、越界和并发陈旧计划；注入写回失败验证库存与槽位记录同时回滚。
- 购买普通拟饵：直接解码 804 和 4/5，断言结果中存在购买物品及合法出厂钩；位置记录缺失不隐藏物品。
- 与 #452 的交点：第一槽为空时，挂载帧仍包含拟饵整树，物理查询仍返回第二槽真实钩。
- 更新旧测试中“卸第一钩后第二钩变成第一槽”的预期，保留出厂钩退包、所有权和陈旧请求校验。
- 必需检查：gofmt、go test ./...、go vet ./...、go build ./...、go run ./tools/doccheck、git diff --check；实际执行结果见 PR 描述，不以自动化测试代替实机验证。

用户已在 4.0.25034 实测确认制作四种组合、装卸、重开页面、重登、重启和普通购买拟饵的背包显示通过。该验证对应相同槽位实现；当前整理版的自动化结果见 PR 描述。没有单独保存修复后新增购买的实机响应，新增购买响应由自动化直接解码覆盖。

## Out of Scope

不修改客户端，不提交反编译资料、真实报文、存档或构建产物；不包含 Launcher hosts、端口配置、UAC 脚本和临时启动诊断。不修改其他制作经济规则，不恢复未知历史槽位，不改钓竿/渔轮装配协议。

## Rollback

回滚程序可忽略额外 KV，FieldsJSON 与旧版紧凑存储兼容。旧程序不会继续维护稳定位置，回退期间的装卸可能再次丢失位置；无需删除玩家物品或逆向迁移数据库。
