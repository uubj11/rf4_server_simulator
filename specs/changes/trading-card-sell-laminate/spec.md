# 卡片出售与卡册塑封

Status: done

## Problem Statement

27/1 出售与 27/4 塑封此前返回失败桩（"卡片覆膜和卡册奖励暂未开放"）：玩家无法出售重复卡变现，集齐卡册后没有塑封封存与奖座奖励。另外掉落卡走单条 4/22 增量推送，开着的卡牌列表不随之刷新。

## Solution

补齐 27/1（只卖散卡、以 def 售价入账、回执幂等）与 27/4（集齐校验、FILETIME 密封时间戳、pnaapkplkfo 奖座幂等补发、塑封后冻结）。掉落/塑封后的客户端同步使用收藏册全量先删后推两代重同步；出售以 27/1 响应 f2 作为唯一库存删除事件。

## User Stories

1. 玩家多张重复卡出售换银，成交价以服务端 def 为准，重试不重复入账。
2. 玩家集齐卡册后塑封：界面转为已塑封渲染（f0 密封快照 + f1 时间戳），弹窗展示奖座，奖座进背包且不重复发放。
3. 塑封后的卡册冻结：入册、取回与重复塑封均被服务端拒绝。
4. 钓获掉卡后无需重开界面，卡牌列表即可见新卡。

## Implementation Decisions

- 在 gameserver 以 hTradingCardSell/hTradingCardLaminate 替换 27/1、27/4 桩；27/1-3 契约 800，27/4 契约 809（llgjfoldbcc）。
- [事实] 27/1 参数 [GuidArr 卡实例, U64 客户端报价]（capstone send 调用点 mov r9b,0x1b + sub=1，0x603d9c）；27/4 参数 [Guid 卡册]（lkokodffmln，0x1805f994d mov byte[rsp+0x20],4）。27/4 响应 wire 类 gglppphenoi/809 = pcnefbpgdhl 派生加 f0 plhpmhpadcg[]，解码序 (描述[], 物品树[], 物品树[], Guid[])；奖励弹窗取 f1 物品树，响应先经 eiihgcpdpbb 应用再回调（2026-11-08 反编译+实机）。
- [事实] 卡册 f1 密封时间戳按 FILETIME 渲染：发 .NET Ticks（0001 纪元）会被 FromFileTime 多算 1600 年，实机显示 3626/11/8。塑封时间 = proto.WindowsFiletimeNow()。
- 出售只接受收藏册容器（native:18）中未入册的散卡；已入册卡（container=card_deck）须先取回，与客户端入口一致。售价取 def 属性 obcephkkfhi，客户端报价仅对账；删除与入账同事务，回执键 card-sell:<uid>:<token>:<main>:<sub>:<call>，同 call 重放返回缓存 ACK。
- 塑封校验 f0 内嵌卡覆盖 def cjmjfnheidh 全部物种；奖座 def 属性 pnaapkplkfo 已有则不重发，ACK 恒带全部奖座树供弹窗展示。奖座构造在事务外（静态库查询不进 SQLite 经济事务），事务内仅 INSERT 与密封字段更新。塑封守卫挂在 changeTradingCardAlbum：f1>0 时入册/取回均拒绝。
- [事实] 客户端刷新（2026-11-08 实机）：4/22 upsert 不替换本地已有物品对象；卡牌列表视图重建滞后一个事件代且同帧推送被合并为一次重建。故掉落/塑封同步通道 = 4/21 全量收藏册 guid + 4/22 全量树，600ms 后跨帧再发一代（resyncTradingCardsTwice）。27/1 的 800.f2 会在出售成功回调前应用已售 GUID 删除；出售路径不再叠加 4/21 或全量卡片重同步，响应后只发 2/1 更新余额。4.0.25034 官服实抓与本地实机均确认 f0/f1 为空、f2 只含已售 GUID；有剩余卡时客户端进入下一张，卖掉末张后的空列表表现也与官服一致（2026-11-17）。
- 客户端基线 4.0.25034；实机验证出售入账/塑封渲染与奖座/掉卡即时可见（2026-11-08）。

## Testing Decisions

- 测试层级：`internal/gameserver` 行为层，使用真实 SQLite、真实 `dispatchRequest` 回执中间件与假客户端隧道，不绕过请求回执。
- 响应顺序：27/1 必须先返回 `obj-800` 响应（marker=-2、call_id 一致），随后只出现一条 2/1 余额推送；`800.f0/f1` 为有类型的空 `args(61)`，`f2` 只包含实际成交卡 GUID。
- 回执重放：复用首次请求的完整 `Body`、`call_id` 和 token，第二次必须命中回执表并返回同一响应体，不能进入“同 call_id 不同请求”的失败分支，也不能再次入账或安排 `afterResponse`。
- 延迟窗口：从首次出售起等待超过旧实现的 600ms 二次全量同步窗口，断言出售与回执重放都不产生额外的 4/21/4/22/2/1 推送。
- 期望值来源：响应 marker/字段形状来自 4.0.25034 27/1 契约；银币增量取 def `obcephkkfhi` 字面量；推送唯一性由假客户端实际收到的隧道记录计数，不由被测代码回算。
- 回滚后变红：恢复 4/21 或 `resyncTradingCardsTwice` 会让推送窗口断言失败；改用不同请求体重放会命中失败分支，无法得到相同响应体；移除经济事务会让重放余额断言失败。

## Out of Scope

- 不调整卡片售价、掉落表、奖座奖励或 27/4 塑封逻辑。
- 不修改 27/1-3 的协议字段形状或客户端版本基线。
- 不重构通用请求回执中间件；本变更只依赖既有回执语义。
- 不覆盖真实客户端长时间断线重连和所有卡册空/满状态视觉表现；由 `docs/client-checklist.md` 的实机项承接。
